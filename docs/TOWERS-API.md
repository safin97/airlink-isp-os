# MikroTik API login in Towers

1. As the owner, open **Towers API → Add profile** (or edit an existing profile).
2. Save the device username and password and select **MikroTik API** or **MikroTik API-SSL** under **Login type**. A blank port uses 8728 for API or 8729 for API-SSL. Custom ports are supported. These are the native RouterOS services, separate from web/REST access; see the [MikroTik API documentation](https://manual.mikrotik.com/docs/developer-guides/api/).
3. On the MikroTik, enable the matching service under **IP → Services**, allow access from the AirLink computer, and give the saved user the appropriate API and read permissions. API-SSL verifies the device certificate by default and requires a suitable certificate. AirLink does not change the router's services or permissions automatically. See [MikroTik service settings](https://help.mikrotik.com/docs/spaces/ROS/pages/103841820/Services).
4. Open **Towers → your tower → Devices**, click **Login via API** on a MikroTik or MikroTik switch row, select the saved profile, and click **Connect**.

The connection card identifies the target device and shows the selected profile's username, connection type, port and TLS verification mode. It requires an explicit profile selection and does not connect automatically. Loading profiles and connecting have separate progress states; failures retain the selection and offer a manual retry. **Reload logins** refreshes available grants. Owners can use **Add saved login** directly in the card; managers without a shared profile see guidance to contact the owner. No stored password is displayed.

After login, the MikroTik panel shows all reported Ethernet/SFP ports, running/disabled status, link speed and duplex, live RX/TX traffic, wireless interfaces and registered clients. It reads legacy wireless and WiFi packages, including mixed installations. Traffic is from the router's perspective; missing readings show a dash, never a fabricated zero. Readings refresh every 15 seconds while the panel is open; refresh pauses during editing or after an error. The native adapter supports RouterOS login; a MikroTik switch must be running RouterOS with API access. This does not log a browser into WebFig.

The full-page workspace has four tabs: **Overview**, **Ethernet**, **Wireless**, and **Settings**. Overview includes traffic summaries, system details, a clickable port map and quick settings links. Ethernet supports searching by port name and filtering running/inactive ports. Wireless shows SSID/signal/traffic cards and registered clients. Settings groups configuration by category. The layout adapts to desktop and phone screens and follows the app's light/dark theme. Close the workspace to return to your tower.

Accounts with **Towers edit permission** can review and save device identity, Ethernet names/enabled state/comments/auto-negotiation/MTU, wireless name/SSID/enabled state/frequency/mode, IPv4 addresses, DNS servers/remote requests and routes. Static IPv4 addresses and routes can also be added or deleted. Each save uses the selected profile and rechecks tower scope, profile grants, current values and dynamic/controller ownership. Dynamic or inherited radio settings remain read-only. These are the supported settings categories, not a full WebFig replacement; firewall, users, security profiles and scripts are not exposed. The device account also needs RouterOS write permission. REST uses fixed POST commands as documented in the [RouterOS REST API manual](https://manual.mikrotik.com/docs/developer-guides/rest-api/).

Open a settings section, click **Edit**, make changes, then **Review → Save to device**. Changes to the management IP, ports, wireless or routes may interrupt access. An uncertain save is never automatically retried; reconnect and inspect the device before trying again. Saves are serialized per device, audited without credentials, and followed by a fresh read. Unsaved forms are not overwritten by automatic refresh.

Existing web/REST profiles keep their original connection type. Profile passwords stay encrypted and cannot be read back. The owner can assign a profile to selected managers. Those managers can select it only for devices within their permitted tower scope; they do not gain access to the owner-only Towers API settings page. Changing or revoking access is enforced again when connecting.

Automated checks exercise the tower login route, native protocol transport, certificate verification/default ports, saved credential selection, manager grants and failure redaction. A connection to your hardware still depends on its service settings, reachability and credentials.
